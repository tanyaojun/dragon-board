# 单一事实源（后端权威，前端消费）

## Overview

池 membership、快照生产、业务口径和分析算法的单一事实源在 QuantBoard 后端；Dragon Board 前端是消费与展示端。前端「自成一套体系」（自建池、自算口径、自产快照）是本仓库反复出现的框架性病灶：两侧各自演化导致对账失败、口径漂移和重复维护。2026-09-18 至 09-21 的两池对账三轮返工（自治池立项 → 盘后对账失败口径修正 → 池源替换）是直接教训。

现状盘点与收敛路线图的唯一权威登记处：`docs/single-source-of-truth-architecture.md`。

## 强制立场

- 新算法、新口径、新采集能力默认落在后端；前端只新增消费与展示。前端要自建任何数据生产或计算前，必须先回答：后端有没有？该不该由后端有？
- 允许存在的双源只有两类，且必须登记在盘点表中：
  1. **保留面**：有明确时效/用途差异的能力（如实时行情链 python-bridge WS → 前端展示，服务于秒级渲染，与研究链用途不同）；
  2. **迁移面**：已登记收敛路径、正在分阶段收敛的历史双源。
- 降级只读缓存（后端不可用时前端的观察面）必须打「降级/非正式」标，且不得反向长成第二事实源；后端恢复后必须回到权威源。
- 双源存在期间，必须有一侧声明为权威、另一侧声明为派生或消费，禁止两边都自称事实源。

## 设计门禁（方案文档必须显式回答）

任何涉及数据链路、池、口径、算法的方案，在设计文档中必须回答三问：

1. 本方案是在消除双源，还是在保留/新增双源？
2. 若保留/新增：权威侧是哪边？收敛路径和阶段是什么？
3. 若声称「前端零改动」：前端侧独立演化（缓存、白名单、本地重算）是否会让本方案的目标（如对账、一致）原理性不可达？

双源问题不允许写进「非目标」静默带过。回答不了就升级为架构议题，由用户裁决后再进入实施。

最小化修改原则保护的是「可验证、可回退」，不是「回避架构裁决」。架构级根因允许架构级目标，但仍用最小步切片执行——小步与根因解决不矛盾（2026-09-21 池源替换即为 `mergeData` 单点小改消除池双源）。

## 落地与验证

- 双源收敛改动必须有对齐验证：golden case、两侧对账脚本或口径测试，证明消费侧读到的事实源与权威侧一致。
- 新增跨端数据流时，测试必须证明前端数据可追溯到后端权威源（provenance/来源标记），降级路径如实打标（配合 `fail-visible-data-pipelines`）。
- 发现未登记的双源时，先补登记（维度、两侧位置、权威侧、收敛路径），再决定动不动代码；不允许「看见了但不说」。

## 反模式

- 「这次先在前端算一版，以后再对齐」——无登记、无收敛路径的双源。
- 「后端不可达时前端先用本地缓存顶上」——可以，但必须打降级标，且后端恢复后必须切回权威源。
- 「把对不上的验收口径改宽就算通过」——对账失败应回溯双源架构，不是修正验收文字（2026-09-21 对 09-19 spec §7.5 的教训）。
