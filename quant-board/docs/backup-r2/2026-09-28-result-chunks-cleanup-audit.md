## 1. 背景与动机

Mongo 全库 14.6GB 中 `backtest_result_chunks` 占 11.4GB(2,895 个文档)。这些 chunks
全部属于 2026-09-21~23 卖点扫描(阶段 A/B)期间产生的 53 个
`ranktrend_early_big_move_v3_lifecycle_fusion` trial run(单份 result 解压文本
~1.68GB,单 run BSON ~280MB)。扫描结论已固化在批次判定卡
(`docs/ranktrend-tier-backtest/exit-scan-batch1~4-verdict.md`、`exit-rules-scan-plan.md`),
大体积 result 明细(21 万 signals、1011 点 equity)对终局结论无增量价值,予以清理。

注意:本轮清理对象是卖点扫描 trial,**不是 themeTrend 回测**——2026-09-25 以来的
7 个 themeTrend run 均为小体积内联存储,不在 chunks 中、不受影响。

## 5. 过程教训(供后续扫描任务引用)

1. **内存**:整包 `json.loads` 1.7GB 文本 → 10GB+ 对象树,在 14.8GB 内存机器上
   与行情服务共存即触顶(2026-09-28 实测 FreeRAM 剩 1GB,与 2026-09-23 冻结事故同源)。
   结论提取这类"只要标量"的任务应解压文本上正则/流式处理,禁全量解析。
2. **后台进程**:会话级后台任务"句柄丢失"≠进程死亡——首轮提取进程被误判已死,
   实际内存膨胀至 14.8GB 仍在跑。杀进程后用分离进程(`Start-Process`)+逐 run
   增量落盘(crash-safe + 幂等跳过)重做。
3. **正则首匹配陷阱**:嵌套结构(controlBacktests/forwardValidation)含同名键,
   首匹配全错;末次匹配=顶层标量,经 3 锚 × 裁决文档数字交叉验证后采用。
