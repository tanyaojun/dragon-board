# KPLViewer 升级分析发现

- 现有桌面端每 6 秒并发拉取大单数据和东方财富基础行情。
- 同花顺 `mainMonitorDetail` 一次返回全天 `list` 与 `title`。
- `list` 提供：性质、手数、成交价、金额、成交时间。
- `title` 提供：代码、名称、现价、涨幅、主买、主卖、交易状态。
- 四类性质可映射为：主力主买→主动买，主力被买→被动买，主力主卖→主动卖，主力被卖→被动卖。
- 同花顺网页版也只使用该接口；股票名称搜索仍依赖东方财富，但桌面端不需要该搜索能力。
- 换手、量比缺失，应显示 `-`。
- 用户接受用成交量与成交价计算成交额；设计中需标明这只是接口样本汇总口径，不等于全市场总成交额。
- 参考图可拆为：顶部行情与阈值、主趋势图、信号点/局部放大、分钟成交柱、分段资金热力、右侧大单明细。
- 可真实实现：顶部已知字段、主买主卖与净额、大单笔数、右侧明细、阈值筛选、既有四类信号、自动刷新。
- 可推导实现：从 `pricechange` 绘制分钟涨幅并反推价格刻度；从大单列表聚合资金趋势、分钟柱和分段资金热力。
- 不能按当前接口真实复刻：完整逐笔成交量、盘口队列、封单、竞价、精确换手、量比及原软件私有“趋势拉升”等公式。

## proxy-server 补充数据审计

- `GET /api/quotes/tencent` 已标准化提供 `f8=换手率`、`f10=量比`，无需东方财富。实测 `002297` 返回换手 `20.56`、量比 `0.82`。
- 同花顺旧涨停池 `/api/limitup/10jqka` 提供 `turnover_rate`、`order_amount`、`order_volume`、`open_num`、`limit_up_suc_rate`、首次/最后涨停时间、`high_days` 和涨停原因。
- 实测截图股票 `002297` 在 2026-06-18 返回换手 `20.5636%`、封单额 `45049860`、封单量 `1588500`、开板次数 `20`、首板、封板成功率 `58.82%`。
- 同花顺涨停池同时返回市场级 `limit_up_count` / `limit_down_count`，可展示当日涨停、炸板、封板率及昨日对比。
- 细分涨停池 `/api/limitup/ths/pools` 的 `volume_money` 也是封单额候选字段，项目既有审计已用真实样本确认。
- `proxy-server /api/opening-signals` 只缓存由前端或桌面端上报的竞价弱转强结果，不采集竞价原始行情。
- KPLViewer 可在 09:20–09:25 持续采样腾讯行情的价格和成交额，自建竞价量价基线；程序未在该时段运行时不能事后可靠补算。
- 同花顺涨停池只能辅助确认冲板/封板，不足以还原竞价过程。

## 用户确认

- 本期排除竞价能力。
- 新工具可依赖 `proxy-server`，由代理统一承接腾讯行情、同花顺涨停池和缓存。
- 工具目录和项目名称从 KPLViewer 迁移为 THSBigOrder。
- 已确认代理架构：新增 `/api/big-order/ths-detail`，客户端并行读取 `/api/quotes/tencent` 与 `/api/limitup/10jqka`；保留旧 `/api/big-order/*` 供 Dragon Board 现有调用者使用。
- 已确认刷新与降级：6 秒并行请求且不重叠；大单失败保留最后成功快照并标记陈旧；腾讯失败相关字段显示 `-`；涨停池区分“非涨停池”和“接口不可用”；代理离线不直连回退。

## 2026-06-20 第二轮图表优化初步发现

- 当前黄线直接绘制同花顺 `pricechange` 涨跌幅；它是分时价格线，不是按成交额加权的分时均价线。
- 当前白线绘制大单买卖净额累计值，并在主图区独立按自身最小/最大值缩放；白线和黄线不共用金融量纲，视觉高低不可比较。这正是截图中白线可能高于黄线的直接原因。
- 底部目前只有固定深色底和金额文本，没有按八个 30 分钟区间的金额强度计算颜色，因此尚未达到参考图的热力表达。
- 当前分钟成交额来自腾讯累计成交额；是否改走 `python-bridge` 不能凭延迟直觉决定，下一步要核对 bridge 是否已有历史/当日分钟线接口、字段完整性和连接恢复机制。
- `python-bridge` 当前只暴露 `/health`、`/status` 和 `ws://127.0.0.1:8765/ws/quotes`，主循环调用 `mootdx Quotes.quotes()` 推送实时 L1 快照；没有已实现的当日分钟线/历史分时 HTTP 或 WebSocket 合同。
- bridge 标准报价已有现价、涨幅、成交量、成交额、昨收、开高低和可选换手率，但没有量比；基础行情可作为更低延迟的实时主源候选，不能单独替代现有全部基础字段。
- bridge 仅在客户端订阅后轮询，且当前 THSBigOrder 是 WinForms HTTP 客户端；直接替换意味着新增 WebSocket 生命周期、订阅、断线恢复和快照缓存，不是简单换 URL。
- 对“当日完整八段成交额”而言，腾讯分钟累计额仍更合适：它能一次返回当日分钟历史；bridge 若程序中途启动，只凭实时 L1 快照无法补齐启动前的 30 分钟区间。
- `pricechange` 的现有测试样本为 `0.5485`，解析器直接将它命名为 `ChangePercent`；但该字段未与腾讯分钟价格交叉验证，当前“黄线=分时涨跌幅”的假设仍需用真实同一时刻数据确认。
- 腾讯分钟源已经同时返回每分钟价格、累计成交量和累计成交额，因此无需新增数据源即可计算标准分时均价：`累计成交额 / 累计成交量`（需先确认腾讯累计成交量单位，再做股/手换算）。
- 真实同花顺样本已确认 `pricechange` 就是涨跌幅：002297 在 09:30/09:31/09:32 分别为 `-0.3103% / 1.8231% / 3.5687%`，与当日价格走势一致。
- 本机 3000 端口当前运行的是未包含新分钟路由的代理版本，`/api/quotes/tencent/minute` 返回 `proxy_route_not_found`；后续同刻比对需从 feature worktree 在独立端口启动代理。
- feature 代理 3011 的真实腾讯数据确认：`cumulativeVolume` 单位为手，标准分时成交均价公式为 `cumulativeAmount / (cumulativeVolume × 100)`。
- 002297 实际均价：09:30 `25.70`、09:31 `25.9728`、09:32 `26.1282`、15:00 `27.9378`；同期成交价为 `25.70 / 26.25 / 26.70 / 28.36`。因此标准黄线通常低于强势上涨中的白色分时价格线，这是合理现象。
- 可行的正确主图合同是：白线使用腾讯每分钟成交价，黄线使用腾讯累计量额计算的 VWAP；同花顺 `pricechange` 可作为分钟价格缺失时的涨跌幅兜底。现有累计大单净额白线应移出价格主图或取消，不能继续与价格共图独立缩放。
