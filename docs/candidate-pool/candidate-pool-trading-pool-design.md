# 候选池 / 交易池 双池方案

**日期**: 2026-06-14
**状态**: 草案
**范围**: Dragon Board 候选池面板、历史交易日志入口、DataTable 右键入口、交易日志语义

## 1. 结论

当前候选池面板把两种语义混在了一起：

- **候选池**：偏策略初筛，回答“这只票值不值得进入跟踪样本”
- **交易池**：偏实盘买点复筛，回答“这只票值不值得继续盯成可执行买点”

本方案建议保留现有候选池自动入池逻辑不变，在候选池工作台中新增交易池视图或独立交易池面板。交易池的自动入池必须建立在候选池已通过的前提上，再做第二道信号共振筛选；真实历史交易日志继续只记录实际 entry/exit。

## 2. 背景

用户当前盯盘时，不是只看 V5 基线矩阵是否通过，而是更看重 DataTable tooltip 中的实时共振信号：

- 方向一致性
- Jump 跃迁置信度
- 多周期动量
- 动量加速度
- 零线交叉
- MACD 金叉 / 死叉

因此，单一“候选池”无法同时表达：

1. V5 回测基线意义上的初筛样本
2. 真实盯盘意义上的买点共振样本
3. 入池后的实时变化和出池状态

## 3. 目标

1. 候选池继续做初步筛选，保留现有自动入池逻辑。
2. 交易池成为二次筛选入口，必须先经过候选池判定。
3. 交易池支持自动入池、自动出池和状态流转。
4. 两个池子的视觉风格统一，但语义不同。
5. 交易池与真实历史交易日志保持边界：交易池服务买点复筛，历史交易日志只记录真实买卖。

## 4. 非目标

- 不在本方案中修改现有候选池自动入池规则本体。
- 不把交易池直接做成自动下单模块。
- 不引入外部大模型。
- 不在第一版新增后端表结构。

## 5. 两池分工

### 5.1 候选池

职责：

- 策略初筛
- V5 基线口径下的候选样本沉淀
- 样本快照保留
- 候选状态流转
- 复盘素材收集

核心判断：

- 候选分层
- Jump 门槛
- 样本质量
- 生命周期
- V5 live execution contract

### 5.2 交易池

职责：

- 复筛买点
- 交易共振确认
- 自动出池判定
- 持续观察 / 已退出 / 已完成

核心判断：

- 综合置信度
- 方向一致性
- Jump 置信度
- MACD
- 动量加速度
- 零线交叉
- 以及这些信号是否持续同向

## 6. 入池链路

### 6.1 候选池入池

入口保持不变：

- DataTable 右键“加入候选池”
- 候选池面板自动入池

候选池负责先判断是否满足当前策略样本条件，保存入池快照。

### 6.2 交易池入池

交易池必须满足两个前提：

1. 该股票已经在候选池中通过初筛
2. 当前实时信号满足交易池二次规则矩阵

也就是说，交易池不是独立捞票，而是**候选池之上的二次筛选层**。

## 7. 交易池规则建议

交易池规则建议拆成两层：

### 7.0 信号源映射

交易池规则必须先落到现有代码字段，再谈阈值和状态。当前可直接复用的信号来源如下：

| 规则项 | 现有代码来源 | 备注 |
|---|---|---|
| 方向一致性 | `stock.rankTrend.technical.signals.direction.signal`，兼容 `stock.directionSignal` | DataTable tooltip 已在使用 |
| Jump 置信度 | `stock.rankTrend.jump.confidence`，兼容 `stock.jumpConfidence` | 候选池与交易池都应可读 |
| 多周期动量 | `stock.rankTrend.technical.momentumProfile`，兼容 `stock.rankTrend.executionStrategy.momentum` | 以 RankTrend 技术层为主 |
| 动量加速度 | `stock.rankTrend.technical.signals.acceleration.signal`，兼容 `stock.accelerationSignal` | 与方向一致性分开判定 |
| 零线交叉 | `stock.rankTrend.technical.signals.zeroCross.signal`，兼容 `stock.crossSignal` | 交易池二次确认项 |
| MACD 金叉 / 死叉 | `stock.rankTrend.technical.macd.cross`，兼容 `stock.macdCross` | 作为出池优先级较高的信号 |
| 候选层级 / 生命周期 | `FusionStrategyProjection.strategyState`、`candidateTier`、`lifecycleAction`、`entryDecision` | 来自候选池投影与执行层 overlay |

交易池不直接读取单一“交易池专用”源，优先复用现有 `FusionStrategyProjection`、`FusionExecutionOverlay`、`RankTrend` technical signals 和 `CandidateExecutionOverlayByCode`。

### 7.1 硬条件

- 候选池已通过
- 方向一致性为 `buy`
- Jump 置信度达到阈值
- MACD 不为死叉
- 生命周期不处于明确 veto

### 7.2 共振条件

以下条件用于区分“观察买点”和“准备介入”：

- 综合置信度
- 多周期动量是否同步为正
- 动量加速度是否为买入
- 零线交叉是否为买入
- 题材/龙头/资金是否协同

建议结果分层：

- `观察买点`
- `准备介入`
- `已介入`

## 8. 自动出池规则

这是当前方案的关键缺口，必须补齐。

交易池的自动出池应基于**实时信号重算**，而不是只依赖入池时快照。

### 8.1 重算机制

建议重算触发源优先复用现有行情刷新周期，而不是另起一套交易池定时器：

- 行情刷新完成后重算交易池状态
- 手动点击“刷新”时立即重算
- 若当前数据源不可用，仅标记数据过期，不强制回退状态

候选分析可复用 `CandidateJournalService.reanalyzeCandidate()`，但交易池应在其上叠加二次规则矩阵，而不是重新写一套独立分析链。

### 8.2 数据过期策略

- TDX bridge 离线、盘后或信号缺失时，保留当前交易池状态
- 额外写入 `data_stale` / `signal_stale` 类标记，避免错误降级
- 不因临时缺源直接把 `已介入` 回退成未知状态

### 8.3 出池优先级

建议出池分三级：

- **强制出池**：生命周期 veto、明确退出信号、MACD 死叉叠加方向转弱
- **强降级**：Jump 置信度跌破阈值、多周期动量同步性破坏、零线交叉转空
- **轻降级**：单项信号转弱，仅从 `准备介入` 或 `观察买点` 降到 `观察中`

建议状态流转：

- `观察买点` -> `准备介入`
- `准备介入` -> `已介入`
- `观察买点` / `准备介入` -> `观察中`
- `观察中` -> `观察买点`
- `观察中` / `已介入` -> `已退出`
- `已退出` -> `观察买点`（可选，需冷却期）
- `已退出` -> `已完成`

建议出池触发条件：

- MACD 死叉
- 方向一致性转弱
- Jump 置信度跌破阈值
- RankTrend 退到失效区
- 生命周期进入 veto
- 多周期动量同步性破坏
- 方向一致性转弱且无法被其它信号抵消

对于 `002129 TCL中环` 这类样本：

- 入池时满足二次规则矩阵 -> 可进入交易池
- 后续若实时信号转弱 -> 降为 `观察中`
- 若 MACD 死叉或明确失效 -> 标记 `已退出`
- 若信号恢复且未过冷却期 -> 可回到 `观察买点`

## 9. 状态建议

### 9.1 候选池状态

- `observe`：待入场
- `candidate`：观察中
- `triggered`：已退出待复盘
- `tracking`：持仓观察
- `reviewed`：已完成

### 9.2 交易池状态

- 观察买点
- 准备介入
- 已介入
- 持仓观察
- 已退出
- 已完成

说明：

- `观察买点` 表示首次通过交易池二次矩阵，但尚未确认真实执行
- `观察中` 表示曾通过但当前转弱，仍保留跟踪价值
- `已介入` 只表示用户确认执行，不等于真实成交已经进入历史交易日志

### 9.3 默认阈值

- Jump 置信度默认建议阈值：`0.8`
- 生命周期 veto：直接强制出池
- 多周期动量同步性破坏：直接触发降级

## 10. 时间与快照

必须同时保留两类信息：

- **入池快照**：记录当时为何进入池子
- **当前实时信号**：决定现在是否继续保留、升级或出池

这能避免历史记录被当前信号覆盖，方便复盘 `002129 TCL中环` 这类“当时满足、现在失效”的场景。

## 11. 面板语义

### 11.1 候选池面板

保持当前候选池的工作台风格，重点展示：

- 策略事实
- 规则矩阵
- 入池理由
- 生命周期
- 候选状态

### 11.2 交易池面板

交易池应作为独立视图或 CandidatePoolPanel 的交易池标签页，不应直接等同于真实历史交易日志。重点展示：

- 买点共振矩阵
- 当前是否仍值得保留
- 自动出池理由
- 执行记录
- 复盘日志

两者视觉风格保持统一，但主标题和文案必须区分清楚。

## 12. 数据与状态

第一版建议只做前端规则层，不新增后端交易池表，也不把交易池直接写进真实历史交易日志。

候选池与交易池之间建议增加显式关联，但可以先以内存投影 / 前端计算方式实现。若后续进入持久化阶段，再考虑独立 `candidateEntryId`。

建议将交易池 entry 视为候选样本的执行层扩展，复用：

- `status`
- `signalsSnapshot`
- `entryReason`
- `tradeHypothesis`
- `entryPrerequisites`
- `invalidationRules`
- `reviewOutcome`
- `executionResult`

必要时在 `signalsSnapshot` 中新增交易池专用子对象，用于保存：

- 二次规则矩阵
- 入池快照
- 出池快照
- 出池原因

后续如果需要持久化交易池，建议使用新的 `trade_type=trading_pool`，并通过 `candidateEntryId` 指向候选池 `thesis` 记录。真实历史交易继续使用 `trade_type=entry/exit`，不与交易池混用。

## 13. 缺失事项

当前还缺少以下内容，未补齐前不应进入完整持久化实现；第一版前端规则层可以先用默认阈值验证：

1. 交易池的精确规则权重
2. 候选池与交易池的重复信号归属
3. 自动出池优先级的最终阈值
4. `观察中` 与 `已退出` 的精确切换阈值
5. `已介入` 的人工确认交互细节
6. 交易池与历史交易日志的最终命名
7. 面板入口调整位置
8. 交易池是否需要独立统计口径

## 14. 第二版：交易池持久化层

第一版只做前端投影，不写入新表；第二版再把交易池固化为独立持久化对象，用来承接长期跟踪、复盘和出池闭环。

### 14.1 目标

- 把交易池从“前端规则层”升级为“可持久化的工作台对象”
- 保持候选池、交易池、真实历史交易日志三者语义分离
- 为自动出池、复入池、复盘统计和跨会话恢复提供稳定载体

### 14.2 数据契约

第二版建议新增或正式启用如下契约：

- `trade_type = trading_pool`
- `candidateEntryId`：交易池 journal 记录的顶层字段，指向候选池中对应的 `thesis` 记录
- `signalsSnapshot.tradingPool`：保存交易池专用快照

其中 `signalsSnapshot.tradingPool` 建议包含：

- `version`
- `entryDecision`
- `entryChecks`
- `entrySnapshot`
- `exitDecision`
- `exitChecks`
- `exitSnapshot`
- `lastRecomputedAt`
- `dataQuality`

### 14.3 状态边界

- `trading_pool` 不是历史真实交易
- `entry` / `exit` 仍然只表示真实买卖记录
- `已介入` 只表示交易池内的执行确认态，不等于历史成交已经生成
- 候选池记录被删除或失效时，交易池记录不应默认级联删除，需显式处理

### 14.4 持久化触发

- 交易池记录可在用户确认后落库
- 若后续支持自动持久化，也必须保留“仅前端投影”的入口
- 已存在的候选池记录不需要强制迁移成交易池记录

### 14.5 文档和接口影响

第二版真正落地时，需要同步检查：

- `quant-board/docs/api-cli.md`
- `quant-board/docs/architecture.md`
- `quant-board/docs/database-migration-plan.md`

如果第二版只做前端投影，则这些文档暂不改动；只有新增 `trading_pool` 语义或字段时才进入同步范围。

## 15. 文档同步计划

若本方案进入实现，需要同步检查：

- `docs/candidate-pool/candidate-pool-workbench-design.md`：补充双池边界和交易池入口说明
- `docs/candidate-pool/task_plan.md`：若新增实施计划，应记录交易池阶段和验收命令
- `quant-board/docs/api-cli.md`：仅当新增 `trade_type=trading_pool` 或 journal 字段时更新

## 16. 推荐的最小落地版本

第一版建议只做：

- 保留候选池现有逻辑
- 在候选池面板内新增“交易池”视图或标签页
- 交易池只显示候选池通过后的对象
- 交易池只做前端规则层重算与自动出池提示
- 保留人工确认 `已介入`

暂不做：

- 自动下单
- 后端新表
- 复杂统计报表
- 外部大模型
- 把真实历史交易日志改名或并入交易池

## 17. 结论

本方案的核心是把“初筛”和“买点复筛”拆开。
候选池负责“筛进来”，交易池负责“筛成买点并持续判断是否还能留在池里”。
