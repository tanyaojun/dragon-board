# THSBigOrder 高置信事件归因设计

## 1. 目标

1. 把“点火/砸盘”从单笔金额标签改为连续订单流事件，只对方向失衡且产生同向价格响应的窗口标记。
2. 把“买活跃/承接好”归属于已确认的点火/砸盘事件，不再作为脱离事件的独立金额标签。
3. 语音只播确认事件，优先减少误报；单只股票通常每天 0 至 5 个事件是观察目标，不是硬性配额。
4. 使用现有秒级成交字段做“窗口归因 + 价格响应”，不声称观察到委托单之间的真实逐单撮合因果。
5. 先落地可解释规则；单日候选池样本不用于宣称阈值最优，也不引入机器学习。

## 2. 数据能力与边界

可用字段为 `Time/Type/Volume/Amount/Price`。Longhu 只有秒级时间，没有委托 ID、成交序号、盘口深度和队列变化；同秒允许合法重复成交。

工程映射采用当前已交叉核验的高置信口径：

- `Type=2`：主动买；
- `Type=4`：主动卖；
- `Type=3`：主力被动买，即卖方驱动成交中的承接；
- `Type=1`：主力被动卖。

输入行必须满足 6 列结构能映射出的合法时间、`Type`、正价格和非负金额。非法占位行只跳过并计数，不参与阈值、订单流或价格计算。窗口不能跨越午休或交易日。

## 3. 自适应大单基线

每个交易分钟、每个主动方向分别计算阈值 `L`：

```text
L = max(500 万, 前 20 个完整交易分钟同 Type 成交额的 P90)
```

前序同 Type 合法样本少于 30 笔时只使用 500 万绝对下限。只使用候选事件之前的完整分钟，避免未来数据泄漏，也避免同一分钟刷新时阈值来回变化。

500 万是本轮高精度语音口径的绝对下限，来源于用户明确要求；P90 用于抑制不同股票活跃度差异。该参数后续只能根据多交易日人工标签和盘中记录调整，不能根据一个交易日直接“训练”。

## 4. 连续点火与连续砸盘

算法先按秒聚合指标，但保留原始成交的合法重复次数。对每个候选结束秒检查其向前 10 秒窗口。

连续点火必须同时满足：

- 至少 3 笔 `Type=2`，且每笔金额均不低于当时的 `L`；
- 窗口内 `Type=2` 金额 / (`Type=2` + `Type=4` 金额) 不低于 70%；
- 从第一笔合格主动买之前的最近有效成交价，到候选结束秒成交额加权价格，上涨至少 3bp；
- 候选结束 8 至 10 秒后存在有效成交，且输入数据时间已经越过候选结束后 10 秒；确认价格至少保留初始涨幅的 50%；
- 与上一条已确认点火事件至少间隔 20 秒。

连续砸盘完全对称：至少 3 笔达到 `L` 的 `Type=4`、主动卖纯度不低于 70%、价格下跌至少 3bp、8 至 10 秒后保留至少 50% 跌幅、同方向冷却 20 秒。

同一结束秒只产生一个方向事件。展示行选择该秒同方向金额最大的真实成交，`FundMarker` 仍写“点火”或“砸盘”，语音金额仍播该真实成交的金额，不把窗口合计伪装成单笔金额。

## 5. 买活跃

“买活跃”只能附着在已确认点火事件的展示行。候选结束后的 8 秒窗口还必须满足：

- 至少 2 笔 `Type=2`；
- 后续 `Type=2` 合计金额不低于事件阈值 `L`；
- 后续主动方向纯度不低于 70%；
- 点火价格保留条件成立。

因此，三笔大买形成点火但随后没有主动买延续时，只播“点火500万”；存在明确延续时才播“点火1000万 买活跃”。

## 6. 承接好

“承接好”只能附着在已确认砸盘事件的展示行，必须同时具备卖压、吸收证据和价格恢复：

- 从砸盘前 10 秒到候选结束，`Type=3 + Type=4` 合计不少于 `2L`，且至少 5 笔卖方驱动成交；
- 以下吸收证据至少满足一项：`Type=3` 占卖方驱动金额不低于 30%，或候选结束后 8 秒内 `Type=2` 反击金额不低于 `L`；
- 确认价格从候选结束后窗口低点恢复至少本次最大跌幅的 50%，且确认秒不再创新低。

“连续 10 笔 100 万卖出，随后 1 笔 1000 万主动买”的例子可作为高概率吸收/反击证据，但结论仍表述为窗口归因，不能表述为已证明该买单逐笔吃掉前十笔卖单。

## 7. 延迟确认与增量语音

价格保留需要未来 8 至 10 秒数据，因此事件展示行可能先以普通成交出现，后续刷新才获得 marker。detector 必须等输入中的最新成交越过候选 `+10秒` 后才冻结结果，避免窗口尚未关闭时 marker 从“点火”升级为“点火 + 买活跃”并重复播报。现有仅按订单指纹识别“新行”的语音跟踪无法播出这种延迟确认，必须同步调整：

- 语音跟踪对象改为 marker 指纹，而不是普通订单指纹；
- marker 指纹包含股票、数据源、交易日、展示行成交指纹和 marker 组合，并继续按出现次数保留合法重复成交；
- 首帧只建立已确认 marker 基线；后续旧行从无 marker 变为已确认 marker 时播报一次；
- marker 消失后重新出现、筛选切换或重复刷新都不重播；
- 关闭语音期间仍推进 marker 基线，重新开启保留现有首帧屏障；
- 同批多个确认事件继续合并为 FIFO 语音批次。

这会有意替代旧测试中“历史普通行后续获得 marker 也永不播报”的合同，否则任何带未来价格确认的事件都无法在盘中播出。

## 8. 代码边界

- 新增 `tools/THSBigOrder/Analytics/BigOrderEventDetector.cs`：只负责输入清洗、阈值、窗口事件和 marker 赋值。
- `THSBigOrderDataProvider.CalculateMarkers` 保持公开签名，内部仅委托 detector，避免改动所有 provider/test stub。
- `BigOrderAnnouncementTracker` 改为跟踪已确认 marker 的计数指纹；语音文本和 `VoiceService` 队列合同不变。
- 不新增配置页、数据库、网络 API、候选事件 UI 或机器学习依赖。

## 9. 测试与验收

自动化测试至少覆盖：

- 单笔 1000 万、三笔 500 万但无价格响应、方向纯度不足均不触发；
- 三笔达标、3bp 冲击和后续保留同时成立才触发点火/砸盘；
- 自适应 P90、低样本回退、午休边界、20 秒冷却、合法重复和非法占位行；
- 点火有/无后续主动买时，“买活跃”分别出现/不出现；
- 真实卖压 + 被动吸收或主动反击 + 价格恢复同时成立才标记“承接好”；
- 旧行延迟获得 marker 时播一次，重复刷新、marker 重现、切筛选和重新开启语音不重播；
- 语音仍输出“股票名 时间 点火/砸盘金额 [买活跃/承接好]”。

交付验证运行 C# runner、THSBigOrder Release 构建和 `git diff --check`。上线后第一个完整交易日人工记录事件时间、窗口证据和误报/漏报；至少积累 20 个交易日后再评估阈值，不以单日信号数量代替质量判断。

## 10. 当前样本基线

2026-07-17 本地归档当前有 28 只股票、169,870 条原始记录；显式清洗后 169,623 条有效、247 条无效占位。旧规则产生 1,869 次点火和 2,025 次砸盘；固定 500 万下限、10 秒连续性、70% 纯度、3bp 冲击、8 至 10 秒保留、20 秒冷却的描述性重放产生 31 次点火和 25 次砸盘。

这些数字只用于证明旧规则过宽和估算播报密度。该日大盘显著下跌，适合检验卖压、砸盘和承接压力场景，但存在明确行情偏置；实现保持买卖对称，不据此单独放宽卖侧阈值。样本只有一个交易日且来自候选池，不能证明新规则有预测收益，也不能证明阈值适合全市场。
