4. UI 和 DataLoader 又切去 HTTP
5. WS 一恢复又切回 TDX

这就是你昨天和今天都看到的“订阅和轮询不停切换”。

2026-04-28 晚间追加结论：

  - `code=2`：稳定返回 `1`，会触发 1 次 callback；回调文本解码为 `选股在下载的本地数据中进行,请确保数据完整`
  - `code=12`：稳定返回 `1`，会触发 2 次 callback；回调关键字分别是 `VIPDOCPATH` 和 `EXTERN`
  - `code=14`：稳定返回 `1`，当前没有观察到 callback
  - `code=3`：进入调用后阻塞，不返回
  - `code=11 / 13`：调用阶段直接触发 `0xC0000005`
- 以上 callback 已确认属于初始化 / 本地文档 / 路径类事件，**还不是十档盘口或实时行情数据**
- `TdxDeep_Func:4` 按官方 `buffer* + len* + hwnd` 形态复刻后仍会阻塞，因此它更像运行中上下文里的内部处理器，而不是可直接外拉的查询接口
- helper 已补充：
  - `--unsafe-deep-func-codes <csv>`：按单功能码隔离探测
  - callback 内存快照：会抓取 `arg1/arg4` 的原地预览，便于判断返回的是文本、路径还是结构块
  - `unsafe func probe` 模式下跳过 `deepUninit / FreeLibrary`：避免结果已经吐出后，进程在 native 清理阶段反崩

这批结果把 `TdxDeep_Func` 的低价值分支基本清空了：

- `2 / 12 / 14` 只能证明 helper 已经进入官方 Deep 运行态
- 它们没有把十档盘口带出来
- 下一条高价值线应当转向 `TdxDeep_Data` 的官方 7 参数调用链，而不是继续用同一套空上下文硬撞 `Func`

`TdxDeep_Data` 的静态调用形态也已补齐：

- `type=1` 调用点：
  - 先分配/准备一块 `0xC4` 长度的本地缓冲
  - 然后调用形态为 `fn(1, edi, 0, 0, ebx, &len0xC4, 0)`
  - 其中 `edi` 不是常量，而是调用现场里的活动值；`ebx` 也不是空指针，而是上文刚准备好的缓冲上下文
- `type=2` 调用点：
  - 调用前会把本地长度描述写成 `0x58`
  - 然后调用形态为 `fn(2, eax, 0, 0, ebx, &len0x58, 0)`
  - 这里的 `eax / ebx` 同样来自调用现场，不能直接用 `0 / hwnd / 空串` 代替

因此，`TdxDeep_Data` 当前的准确判断是：

- 它确实比 `Func:2/12/14` 更像数据通道
- 但它依赖官方运行中对象、缓冲和状态机
- 在独立 helper 进程里，**还没有足够上下文去安全复刻它**
